A Sensor That Isn’t There

One of the Mark-1 Exosleeve's most important sensors doesn’t physically exist: how software replaces hardware for both touch and vision.

A sensor, in the traditional sense, is a piece of hardware built to measure one thing well: a pressure transducer measures force, a thermal camera measures heat, a lidar unit measures distance. The software just reads the number off.

The Mark-1 Exosleeve’s control stack does something different: one of its most important sensors doesn’t physically exist.

The Core Idea

A sensor inferred entirely in software.

Case One: A Pressure Sensor With No Transducer

The prosthetic’s pneumatic arms have no physical pressure sensor on the McKibben muscles. Instead, hardware/pressure_reader.py maintains a live model of what the pressure should be, given every valve command issued, and reads the gap between model and reality as signal:

"""
Software pressure sensor — derives physical state from valve commands
and the McKibben muscle model without physical pressure transducers.

  Faster-than-expected pressure rise  → encountering resistance (contact made)
  Slower-than-expected pressure rise  → free movement, no load
  Pressure plateau below target        → maximum muscle extension reached
  Sudden pressure drop                 → structural event (cable slip, etc.)

These deviation signals feed LimbStateEstimator as "soft sensor readings" —
they carry the same information a physical pressure transducer would,
derived entirely from the physics of the system.
"""

The model itself is a first-order lag (the same math you’d use to describe a capacitor charging) updated every tick against the commanded target:

def update(self, dt: float) -> PressureReading:
    # First-order lag
    alpha          = dt / _TIME_CONSTANT_S
    self._modelled = self._modelled + alpha * (self._target - self._modelled)
    self._modelled = max(0.0, min(MAX_PRESSURE_KPA, self._modelled))

    # Deviation detection
    expected_at_this_time = self._expected_pressure(now - self._last_command_time)
    deviation = 0.0
    if expected_at_this_time > 1.0:
        deviation = (self._modelled - expected_at_this_time) / expected_at_this_time

    # Contact detection: pressure rising faster than free-movement model
    contact = deviation > _CONTACT_DEVIATION_THRESHOLD

    # ROM limit: pressure plateauing well below target
    rom_limit = (
        self._target > _MIN_PRESSURE and
        self._modelled < self._target * (1.0 - _ROM_PLATEAU_THRESHOLD * 3) and
        now - self._last_command_time > _TIME_CONSTANT_S * 5
    )

    load_n = ValveDriver.pressure_to_force(self._modelled, self._contraction_ratio)
    ...
    return PressureReading(
        modelled_kpa=round(self._modelled, 2),
        deviation=round(deviation, 4),
        contact_detected=contact,
        rom_limit_reached=rom_limit,
        load_estimate_n=round(load_n, 3),
        confidence=round(self._confidence, 3),
    )

PressureReading.is_anomalous and ArmReading.in_contact then flow straight into the reasoning core as facts — “contact detected,” “range-of-motion limit reached” — the same category of input a physical transducer would produce, generated entirely from a physics model of the actuator plus the record of what was commanded. No transducer, no wiring harness, no failure mode where the sensor itself breaks — because there’s no physical sensor to break.

No transducer, no transducer failure.

Case Two: Turning a Camera Into Structured Perception

The Cognitive Vision Engine (my version of "computer vision" aka CVE) applies that same idea to vision. Raw frames aren’t handed to a model to caption — they’re decomposed into a grid of PerceptualAtoms, grouped into objects, and serialized into a symbolic scene description the deterministic reasoner can actually query.

Object segmentation runs on Union-Find over color family, not per-pixel flood-fill, merging same-family neighbors in a single near-linear pass, then scoring each resulting region for salience:

# Step 5: Union-Find connected components on color family
for r in range(rows):
    for c in range(cols):
        idx = r * cols + c
        if c + 1 < cols and fam[r][c] == fam[r][c+1]:
            union(idx, idx + 1)
        if r + 1 < rows and fam[r][c] == fam[r+1][c]:
            union(idx, idx + cols)

# Step 6: saliency scoring
rel_area = area / total
size_pen = 0.05 if rel_area > 0.45 else (0.35 if rel_area > 0.25 else 1.0)
saliency = avg_e * (area ** 0.5) * (1 - border_frac * 0.85) * size_pen

is_bg = (
    (rel_area > 0.12 and avg_e < 0.06)
    or border_frac > 0.35
    or rel_area > 0.30
)

Color itself is classified in HSL (Hue, Saturation, and Lightness) rather than raw RGB (Red, Green, and Blue), specifically because low-saturation regions (JPEG artefacts, shadow pixels) produce false blues and purples under naive thresholds:

# LOW SATURATION — hue is numerically unstable here.
# JPEG artefacts / cool shadows produce phantom blues and purples.
if s < 0.22:
    if l < 0.32: return {'color': 'dark-gray',  'family': 'gray'}
    if l < 0.62: return {'color': 'gray',        'family': 'gray'}
    return          {'color': 'light-gray', 'family': 'gray'}

# Blue/teal/purple zone — require HIGH saturation to avoid shadow artefacts
if h < 250:
    if s < 0.45: return {'color': 'gray', 'family': 'gray'}  # main blue false-positive fix
    if l < 0.32: return {'color': 'dark-blue', 'family': 'blue'}
    return          {'color': 'blue', 'family': 'blue'}

Every object that survives scoring gets flattened into one line of a symbolic scene string. This is the literal sensor output the reasoning core operates on:

parts.append(
    f"  OBJ id={obj.object_id} "
    f"color={obj.color_name} family={obj.color_family} "
    f"size={obj.size_class} area={obj.area} "
    f"at=[{r0},{c0}→{r1},{c1}] "
    f"centroid=[{obj.centroid[0]:.1f},{obj.centroid[1]:.1f}] "
    f"lum={obj.mean_luminance:.2f} "
    f"depth={depth_str}"
)

No embedding, no probability distribution: a typed, citable fact per object, exactly the format the deterministic reasoning core expects everywhere else in the system.

Why Software-Defined Sensing Matters

  • No transducer, no transducer failure. The pressure “sensor” is a physics model plus a command log, there’s nothing to wear out, miscalibrate, or short.
  • Cost and adaptability. A budget camera plus a deterministic interpretation stack replaces purpose-built vision hardware, and updating the interpretation layer changes what the same physical input can detect (not perfectly but better than nothing).
  • Explainability. contact_detected, rom_limit_reached, saliency — every derived signal traces back through an inspectable model, not a black-box activation. When the system says “contact made,” you can see why.

The Bigger Pattern

This is the same philosophy behind AETHER but applied to perception instead of reasoning: don’t rely on an opaque model to intuit meaning from raw signal.

The end goal: build a deterministic interpretation layer, in software, that turns cheap or nonexistent hardware into a sensor with the reliability profile of something purpose-built, and the traceability of something you can actually debug.
